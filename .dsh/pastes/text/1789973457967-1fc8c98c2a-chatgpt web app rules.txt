### Root Cause Analysis: "The current model does not support images: switch to a model that does"

---

### 1. Where Does This Error Come From?

When you submit a message with an attached image, DeepSeek Harness performs a backend admission check in `session-controller`:
```typescript
if (hasImage) {
  const model = await this.ctx.llm.resolveModelInfo(current.provider, current.model);
  if (model.inputModalities !== undefined && !model.inputModalities.includes('image')) {
    throw new RemoteError('session/attachment-invalid', 'Model does not support image input', {
      reason: 'MODEL_DOES_NOT_SUPPORT_IMAGES'
    });
  }
}
```
When `session-controller` rejects the turn with `MODEL_DOES_NOT_SUPPORT_IMAGES`, the web UI frontend catches it and displays the toast:
> *"The current model does not support images: switch to a model that does"*

---

### 2. Why Did Vision Toolkit Fail to Intercept?

In our previous step, we set `acceptsImages: false` in `providers.js` so that DeepSeek would correctly resolve as text-only (`inputModalities: ['text']`). 

However, `@anionex/dsh-vision-toolkit` did not create the image-handling variant wrapper because of a bug in `dsh-webcode-bridge`:

1. **`listModels()` Omitted `inputModalities`**:
   In `C:\Users\Zubaydulla\.dsh\profiles\web\node_modules\dsh-webcode-bridge\lib\index.js` (line 762):
   ```javascript
   async listModels(provider) {
     return WEB_MODELS.filter((m) => !MODEL_ALIAS_IDS.has(m.id)).map((m) => ({
       provider,
       id: m.id,
       name: m.name
       // ❌ inputModalities is missing!
     }));
   }
   ```
2. **Vision Toolkit's Eligibility Check Failed**:
   `dsh-vision-toolkit` scans all provider models using `llm.listModels()` and checks:
   ```typescript
   export function shouldWrapModel(info) {
     return Array.isArray(info.inputModalities) && !info.inputModalities.includes('image');
   }
   ```
   Because `inputModalities` was `undefined` in `listModels()`, `shouldWrapModel` evaluated to `false`.
3. **The Vision Wrapper Was Never Registered**:
   `dsh-vision-toolkit` assumed `dsh-webcode-bridge` had unknown modalities and skipped registering `vision-toolkit-webcode`. As a result:
   - No image-capable variant was created.
   - The UI was left bound to the raw text-only model.
   - Submitting an image was immediately blocked by the `session-controller` guard.

---

### 3. Proposed Fix

We need to update `listModels(provider)` in `dsh-webcode-bridge/lib/index.js` (both in `C:\tools\dsh-web-bridge-main` and the active profile's `node_modules`) to include `inputModalities`:

```javascript
async listModels(provider) {
  return WEB_MODELS.filter((m) => !MODEL_ALIAS_IDS.has(m.id)).map((m) => ({
    provider,
    id: m.id,
    name: m.name,
    inputModalities: m.acceptsImages === true ? ['text', 'image'] : ['text'],
  }));
}
```

#### What this accomplishes:
1. `listModels()` will correctly announce that DeepSeek is text-only (`inputModalities: ['text']`).
2. `dsh-vision-toolkit` will detect this and automatically register the `vision-toolkit-webcode` variant wrapper (`inputModalities: ['text', 'image']`).
3. The Web UI will route image attachments through the Vision Toolkit pipeline:
   - The backend `session-controller` check passes without throwing errors.
   - Attached images are transcribed into detailed visual descriptions via `vision_glance` / OCR.
   - Clean descriptive text is submitted to DeepSeek Web, completely bypassing `chat.deepseek.com` DOM upload hangs and eliminating `WEB_NO_PROGRESS`.
