- (decision) Treat approved PRD, hardened Forge, and final UX artifacts as ground truth. Treat technical research as research input only, not pre-approved architecture.
- (decision) Preserve the locked one-day AI/Topic semantics: Topic identity is District + Mahalla + Uzbekistan calendar day + same underlying situation; matching never crosses midnight; contextual AI uses complete required raw Accepted Evidence from all same-day Topics in the same Mahalla; RAG/vector retrieval/summaries/recent-window/cross-day memory cannot replace this context; context overflow is explicit failure rather than truncation.
- (decision) Preserve future-only AI configuration semantics and avoid automatic replay of completed old message-level relevance/category/topic-assignment decisions when new evidence triggers Topic-derived recalculation.
- (decision) Architecture refinement scope includes deterministic context assembly, compact lossless evidence serialization, stable ordering, idempotent/retry-safe AI, concurrency/stale-snapshot protection, efficient Topic-derived recalculation, AI configuration/profile version traceability, structured-output validation/failure handling, optional correctness-neutral prompt caching, and privacy-safe observability.
- (decision) Do not introduce embeddings, vector databases, HNSW, reranking, full-history RAG, or historical semantic retrieval in MVP unless a later concrete requirement cannot be met otherwise.
- (decision) AD-1 approved by user: use a hexagonal modular monolith. Keep one cohesive application/codebase and MVP deployment boundary; use domain-oriented modules; place project-owned ports at meaningful external/stateful boundaries; keep provider SDKs and infrastructure behind adapters; allow HTTP/webhook and worker runtime processes from the same codebase without turning them into microservices.
- (rationale) AD-1 minimizes operational and distributed-systems complexity at MVP scale while protecting provider neutrality, domain-rule consistency, testability, and agent-driven implementation from infrastructure coupling.
- (rejected) Traditional loose layering without enforced adapter boundaries: simpler initially but more likely to let AI/Telegram/database concerns leak into domain logic and drift across independently generated modules.
- (rejected) Event-driven microservices: adds network contracts, distributed failure modes, deployment/observability burden, and transaction complexity without an approved MVP scaling or organizational need.
- (decision) AD-2 approved by user: use a pnpm TypeScript workspace on Node.js 24 LTS, Fastify 5.x for the private API and Telegram webhook, shared HTTP/worker backend modules, and a React 19.2 SPA built with Vite 8.x and minimal React Router; start on TypeScript 6.0.x and do not add Next.js/SSR/RSC/server actions without a concrete future requirement.
- (rationale) AD-2 keeps the greenfield stack cohesive in JavaScript/TypeScript, separates runtime entrypoints without splitting the application, and avoids server-rendering machinery the private authenticated product does not require.
- (rejected) Next.js/full-stack React: no public SEO/SSR requirement and it does not remove the need for a durable worker runtime.
- (rejected) TypeScript 7 for MVP baseline: current release is production-ready but lacks the programmatic compiler API until the newer API line lands; TypeScript 6 remains the lower-friction ecosystem baseline without changing architecture.
- (decision) AD-3 approved by user: PostgreSQL 18.x is the sole MVP system of record and pg-boss 12.x is the PostgreSQL-backed durable job mechanism. Persist authoritative state and consequential jobs atomically when required, keep business operations idempotent, and use keyed queue serialization only as coordination rather than the correctness boundary.
- (rationale) AD-3 avoids Redis/message-broker infrastructure and database-to-broker dual-write gaps while supporting durable retries, keyed FIFO coordination, and transactional enqueue at the approved MVP volume.
- (rejected) Redis/BullMQ or another broker: adds another stateful service, backup/monitoring/failure semantics, and usually an outbox bridge without a demonstrated scale requirement.
- (rejected) Graphile Worker: viable PostgreSQL queue but its documented abandoned-lock recovery window is a worse fit for prompt recovery than pg-boss heartbeat/dead-worker behavior.
- (decision) AD-4 approved by user: use stable Drizzle ORM 0.45.x with PostgreSQL/node-postgres and Drizzle Kit 0.31.x; TypeScript schema definitions own codebase schema shape, migrations are generated/reviewable/version-controlled SQL, and direct schema push is forbidden for shared/production databases.
- (rationale) AD-4 preserves explicit PostgreSQL semantics and reviewable migrations while reducing schema/type synchronization work for agent-driven implementation.
- (rejected) Kysely: strong thin query builder, but leaves more schema/type synchronization machinery to project conventions.
- (rejected) Prisma: more abstraction/generated-client machinery than needed for a PostgreSQL-specific design that will intentionally use native constraints/transactions where appropriate.
- (rejected) Raw node-postgres everywhere: maximum control but unnecessary hand-written row/type mapping and greater agent inconsistency risk.
- (decision) AD-5 approved by user: every context-dependent AI operation uses a deterministic complete same-day Mahalla snapshot from PostgreSQL; raw evidence remains verbatim, serialization only removes repetitive structure, ordering is original Telegram timestamp then Telegram message ID then internal evidence ID, and each snapshot carries contextRevision, fingerprint, and serializer version. Complete-context overflow fails explicitly.
- (rationale) AD-5 preserves the locked product semantics while making context assembly reproducible, token-efficient in representation, traceable, and testable without a duplicate canonical prompt store.
- (rejected) Materialized daily context blob: adds invalidation/duplication/retention complexity and stale-context risk at a scale that does not require it.
- (rejected) Topic summaries/recent-window/semantic retrieval: changes the locked evidence semantics rather than optimizing their implementation.
- (decision) AD-6 approved by user: use optimistic concurrency with Mahalla/day contextRevision. AI calls never hold a database transaction; validated results commit only if expected revision and subject validity still match. Revision mismatch is STALE_SNAPSHOT and commits nothing.
- (rationale) AD-6 keeps provider latency outside database locks while making the database revision/CAS boundary, not queue ordering, the final correctness check.
- (decision) AD-7 approved by user: Topic-derived fields are one atomic recalculable projection; only directly affected Topics become refresh targets, each Topic tracks required/applied derived generation, and pending generations coalesce to the newest required state while every refresh still uses complete required same-day Mahalla context.
- (rationale) AD-7 prevents all-Topic fan-out and obsolete intermediate AI work without dropping evidence or replaying completed historical message-level decisions.
- (decision) AD-8 approved by user: all production AI runs through a Mahalla Ovozi-owned typed gateway with provider-specific SDKs/errors confined to adapters; use Zod 4 operation schemas with a portable JSON-Schema subset, immutable versioned AI profiles, structural plus semantic output validation, separate logical-operation/attempt identities, normalized explicit failures, and no partial commit. Prompt caching is optional adapter-only behavior.
- (rationale) AD-8 makes provider neutrality an application-boundary property instead of promising provider interchangeability with identical quality; immutable profiles and separate attempts preserve auditability and retry/cost traceability.
- (rejected) Provider SDK calls throughout application code: leaks provider contracts and failure semantics into domain/application modules.
- (rejected) A cross-provider SDK as the architecture boundary: can be evaluated inside adapters later, but the project should own the stable application contract.
- (decision) AD-9 approved by user: use project-owned PostgreSQL-backed username/password authentication, Argon2id password hashing, opaque revocable database sessions with hashed server-side tokens and Secure/HttpOnly/SameSite=Strict browser cookies, server-derived ActorContext, explicit District scope and District-preserving database constraints, encrypted District Telegram bot tokens under deployment-held versioned keys, and no PostgreSQL RLS for MVP.
- (rationale) AD-9 matches the private no-registration/no-email product model, keeps revocation/lifecycle deterministic, and uses application/repository/constraint layers for tenant isolation without adding a second RLS authorization system prematurely.
- (rejected) Better Auth for MVP identity core: its current user model requires email even when username authentication is enabled, which would force an unused/fake identity field into the product model.
- (rejected) JWT authorization: weaker fit for predictable revocation, role/lifecycle changes, and this private low-concurrency application.
- (decision) AD-10 approved by user: use same-origin versioned JSON REST through Fastify, shared browser-safe Zod API contracts, TanStack Query 5.x for remote server state, React local state for ephemeral UI/form state, District-scoped query keys, atomic Product Owner District switching with cancellation/cache purge/late-response rejection, opaque cursor pagination, no optimistic authoritative lifecycle success, and sanitized stable API errors.
- (rationale) AD-10 gives implementation agents one simple API/state model while directly encoding the approved cross-District stale-state security UX contract.
- (rejected) GraphQL, tRPC, BFF, Redux, and Zustand for MVP: no current requirement offsets the additional conventions/infrastructure.
- (decision) AD-11 approved by user: deploy on one Linux host with Docker Compose and Caddy as the only public edge; run HTTP and worker from the same backend image/codebase; use continuous PostgreSQL WAL archiving plus pgBackRest to encrypted off-primary S3-compatible storage; verify RPO <=1h and RTO <=8h with isolated restore drills; block restored service until deletion/lifecycle reconciliation; use OpenTelemetry traces/metrics plus structured privacy-safe logs; keep product System Health independent from engineering telemetry; measure one-day AI context/cost/latency/retry/overflow/grouping quality instead of preemptively introducing RAG.
- (rationale) AD-11 respects the explicitly accepted single-server availability limitation while providing durable recovery evidence and vendor-neutral observability without Kubernetes or multi-node operational overhead.
- (rejected) Kubernetes/Swarm/multi-host orchestration for MVP: no approved availability or throughput requirement justifies the operational cost.

- (decision) `contextRevision` advances only for state that can alter canonical AI input. A derived-projection-only write does not advance it unless that field is explicitly part of a canonical AI operation input, preventing derived refreshes from causing meaningless stale-work cascades.
- (decision) Logical AI work pins its immutable AI profile version when the logical operation is created; retries of that logical operation use the same profile. A newer Topic generation created after profile activation creates/supersedes work using the active profile rather than mutating the older logical operation.
- (decision) Background jobs carry explicit District scope and re-check relevant lifecycle/access state before external or AI side effects. Product Owner cross-District/global operations use dedicated explicit global administrative contracts; absence of District scope never means global access.
- (decision) Disaster-recovery reconciliation requires a minimal current deletion tombstone source outside the restorable PostgreSQL backup history so an older database restore can prove which Districts must remain deleted; it stores privacy-safe lifecycle identifiers/metadata, not resident evidence or secrets.
- (decision) Audit records are privacy-safe operational/admin metadata: actor, District, action, timestamp, outcome, and safe identifiers; raw resident evidence and credentials are not audit payloads.
