## 3. Mechanism corrections found while re-verifying

Per the standing rule (artifacts are analysis, not proof), the highest-ranked candidates were re-verified at their cited source before being ranked. **Two mechanisms were wrong.**

### `L4-P01-01` — the shared cache key is real; the "different payload shapes" claim is FALSE

- **What holds:** both hooks really do declare `queryKey: ['district-mahallas', districtId]` — `apps/web/src/topics/useDistrictMahallas.ts:10` and `apps/web/src/topics/district-topics-client.ts:134` (grep across `apps/web/src` returns exactly these two). The barrel `topics/index.ts:8` and the alias re-export `district-topics-client.ts:141` mean **two different functions are both importable under the name `useDistrictMahallas`**, and both are actually used: `components/topics/MahallaSelect.tsx:4,19` (0-arg version) and `components/ai/SignalMonitoringTable.tsx:38,170` (1-arg version). The name collision is real and load-bearing.
- **What is FALSE:** the artifact claims the two endpoints "return *different* payload shapes" whose Zod schemas differ, so "whichever hook is served a foreign entry will hand a structurally wrong object to a consumer". **They do not differ.** `packages/api-contracts/src/topics.ts:414` is `export const DistrictMahallasResponseSchema = HokimMahallasResponseSchema;` and `:415` is `export type DistrictMahallasResponse = HokimMahallasResponse;`. They are **literal aliases**, and `HokimMahallasResponseSchema` is `z.object({ mahallas: z.array(z.string()) })` (`:291-293`). `hokim-topics-client.ts:105` returns `string[]` by reading `response.mahallas`; `district-topics-client.ts:132-139` returns the whole `DistrictMahallasResponse`. Both ultimately expose the same `string[]` list.
- **Therefore the stated corruption mechanism cannot occur.** A cache entry written by one is not "structurally wrong" for the other — both validate to `{ mahallas: string[] }`.
- **What survives is still real, and narrower:** the two hooks disagree on `staleTime` (**15 min** at `useDistrictMahallas.ts:13` vs **60 s** at `district-topics-client.ts:137`) and on `enabled` (role-gated `DISTRICT_HOKIM` vs merely `Boolean(districtId)`). So freshness becomes mount-order dependent, and one hook can be gated on while the other is gated off against a shared entry. That is a genuine correctness/freshness defect — **just not the payload-corruption one the artifact describes.**
- **Effect on the ACs:** AC(1) ("no two `useQuery` sites share a key with different URL paths") still stands and is satisfiable. AC(3) ("the barrel exports at most one symbol named `useDistrictMahallas`") still stands. Any test written to reproduce "wrong object shape from cache" would **fail to reproduce**, because the shapes are identical — a test must instead assert freshness/gating divergence.

### `L3-P03-08` — the read-path write is real, but not through the named table

- **What holds:** `queryHokimBoard` (`topic-query-engine.ts:470`) does perform a **write inside a read path**: it reads `userDashboardVisits` (`:507-512`) and then `db.insert(userDashboardVisits).values(...)` (`:517`). This is a GET-triggered mutation and the finding's category (`hidden-dependency`) is correct.
- **Correction:** a grep for `user_dashboard_visits` (snake_case) in the engine returns **zero** matches — the table is referenced through the Drizzle symbol `userDashboardVisits` (`topic-query-engine.ts:6` import, `:507-517` use). Anyone re-verifying this finding by its snake_case name will wrongly conclude it no longer exists. **Grep for the symbol, not the table.**
- **Verified live.** No change to severity.
